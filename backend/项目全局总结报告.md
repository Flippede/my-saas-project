# 《项目全局总结报告》

## 1. 项目背景与技术栈概览

- 一句话总结：这是一个面向“AI 内容生产 + 会员支付 + 微信扫码登录”的微型 SaaS 后端，当前以 FastAPI 提供统一 API 网关与业务闭环能力。  

### 核心技术栈

- 后端框架：`Python + FastAPI`
- 数据存储：`SQLite`（本地文件库 `x_creator.db`）
- 核心第三方库：
  - `requests`（调用微信 API、DeepSeek API）
  - `cryptography`（微信支付 V3 签名验签、AES-GCM 解密）
  - `pydantic`（请求/响应模型）
- 运行与服务：
  - `uvicorn`（ASGI 启动）
  - `CORSMiddleware`（跨域）
- 构建/工程形态：
  - 无前端工程化构建（仓库内无 React/Vue 等前端项目）
  - 无容器编排与 CI 配置（当前仓库未见）
- 架构文档：`AI_Architecture_SOP.md`（约束网关模式与工具模块规范）

---

## 2. 核心功能与业务清单

> 当前仓库存在 **两套 FastAPI 入口**：`main.py`（轻量版网关）与 `app.py`（完整业务版，含登录/支付/会员/工具）。  
> 从实现完整度看，`app.py` 是当前主业务实现。

### A. 会员与鉴权能力

1. `Authorization: Bearer <token>` 令牌校验（`app.py`）
   - 校验 token 是否存在
   - 校验 `status=1`
   - 校验 `expire_date` 未过期
2. 旧版固定 token 校验（`main.py`）
   - 只接受 `test_vip_token_888`
   - 用于简化版 `POST /api/v1/tools` 入口

### B. 微信服务号扫码登录

1. 生成登录二维码：`GET /api/v1/auth/get_login_qrcode`
   - 生成 `scene_id`
   - 调微信 `qrcode/create`
   - 创建 `login_sessions(scene_id, status=pending)`
2. 轮询登录状态：`GET /api/v1/auth/login_status?session_id=...`
   - pending：返回等待状态
   - success：查/发 token，返回登录态
3. 微信事件回调复用：`/api/v1/wechat/webhook`
   - 解析 XML 事件（`SCAN`/`SUBSCRIBE`）
   - 写入登录成功态并绑定 `openid`
   - 若新用户则写入 `users`

### C. 微信支付 + 自动发卡

1. 创建订单：`POST /api/v1/payment/create`
   - 从 token 反查 `openid -> users.id`
   - 生成订单号并入库 `orders`
   - 调微信 Native 下单，返回 `code_url`
2. 微信支付回调：`POST /api/v1/wechat/webhook`（JSON）
   - 验签（平台公钥）
   - 解密 `resource.ciphertext`（AES-GCM）
   - 校验金额与订单
   - 成功后更新 `orders.status=success`
   - 自动签发 30 天 token，并更新用户 VIP
3. 查询支付状态：`GET /api/v1/payment/status?order_id=...`
   - 返回 pending/success
   - success 时附带 token

### D. AI 工具网关能力

1. `POST /api/v1/tools`（`app.py`）
   - 受 token 保护
   - 当前返回 MVP mock 剧本文案
2. `POST /api/v1/tools`（`main.py`）
   - 按 `tool_id` 分发
   - 已接 `script_generator`，调用 `tools/script_generator.py`
   - 实际执行 DeepSeek 生成 3 条带货脚本

### E. 用户信息与健康检查

- `GET /api/v1/user/info`：返回用户 ID、昵称模板、VIP 状态、到期时间
- `GET /health`：服务健康状态
- `POST /api/v1/ping`（仅 `main.py`）：连通性探针

### 核心业务数据流向

1. **登录流（扫码）**  
   前端请求登录二维码 -> 后端生成会话并调用微信 -> 用户扫码触发微信 XML 回调 -> 后端把会话置为 success 并绑定 openid -> 前端轮询拿到 token。

2. **支付流（订阅）**  
   前端携带 Bearer token 下单 -> 后端识别用户并建单 -> 微信支付回调（JSON）入站 -> 后端验签/解密/验金额 -> 更新订单成功 + 发 token + 激活 VIP -> 前端查单拿支付结果。

3. **AI 工具流（剧本生成）**  
   前端提交 tool_id/payload -> 网关鉴权与分发 -> `script_generator` 组装提示词并请求 DeepSeek -> 返回统一 JSON 结果给前端展示。

## 3. 核心目录结构与文件说明

> 已按约束忽略依赖/构建产物（如 `node_modules`、`dist`、`build`、`.git`、`.next`）。  
> 当前项目核心代码目录非常精简。

```text
ai_tools_backend/
├─ app.py
├─ main.py
├─ requirements.txt
├─ AI_Architecture_SOP.md
├─ tools/
│  └─ script_generator.py
├─ .cursor/
│  └─ rules/
│     └─ *.mdc (大量 AI 规则模板)
└─ __pycache__/                (运行缓存，非业务源码)
```

### 文件/目录职责映射（业务维度）

- `app.py`
  - 当前最完整业务服务入口
  - 承担：登录二维码、登录状态轮询、微信回调双模处理（XML+JSON）、支付下单/查单、token 鉴权、用户信息查询、MVP 工具接口
  - 包含数据库初始化与轻量迁移逻辑（`users/orders/tokens/login_sessions`）

- `main.py`
  - 轻量统一网关入口（偏“早期/简化版”）
  - 承担：固定 token 鉴权、工具分发（按 `tool_id`）、探针接口、健康检查
  - 适合作为“最小闭环样板”，但与 `app.py` 功能重叠

- `tools/script_generator.py`
  - 具体业务工具模块：抖音带货脚本生成器
  - 承担：从 payload 读取主题与关键词 -> 构建 system/user prompt -> 调用 DeepSeek Chat -> 返回统一结构化结果

- `AI_Architecture_SOP.md`
  - 项目架构规范与维护要求
  - 描述网关协议、工具模块约定、支付/登录链路快照
  - 用作 AI/开发协作的“架构准入文档”

- `requirements.txt`
  - 当前仅声明 `fastapi/uvicorn/pydantic/requests`
  - 与实际代码依赖存在偏差（见优化建议）

- `.cursor/rules/*.mdc`
  - AI 助手行为规则库（提示词/角色规范）
  - 非运行时业务逻辑，但影响 AI 协作流程与产出风格

## 4. 重要接口与核心契约 (API & Interfaces)

## A. 核心 API 路由（按业务分组）

### 1) 登录域

- `GET /api/v1/auth/get_login_qrcode`
  - 入参：无
  - 出参：`{ scene_id, qrcode_url, expires_in }`
  - 业务：创建扫码登录会话并返回微信二维码 URL

- `GET /api/v1/auth/login_status?session_id=...`
  - 入参：`session_id`
  - 出参（pending）：`{ status: "pending", session_id }`
  - 出参（success）：`{ status: "success", session_id, openid, token }`
  - 业务：轮询登录结果，成功时返回可用 token

### 2) 支付域

- `POST /api/v1/payment/create`（需 Bearer token）
  - 入参：请求体可为空（用户身份主要来源于 token）
  - 出参：`{ order_id, code_url, amount, status }`
  - 业务：创建微信 Native 支付订单并返回扫码链接

- `POST /api/v1/wechat/webhook`
  - 入参：
    - GET：微信服务器校验（`echostr`）
    - POST XML：服务号扫码事件
    - POST JSON：支付通知（含密文）
  - 出参：统一成功确认（`SUCCESS`/`success`）
  - 业务：统一承接登录事件与支付回调，驱动订单和会话状态机

- `GET /api/v1/payment/status?order_id=...`
  - 入参：`order_id`
  - 出参：`pending` 或 `success + token`
  - 业务：前端轮询订单支付状态

### 3) 工具域

- `POST /api/v1/tools`（`app.py`）
  - 入参：`{ prompt }`（`ToolRequest`）
  - 出参：MVP mock 剧本文案
  - 业务：受鉴权保护的工具统一入口（当前返回 mock）

- `POST /api/v1/tools`（`main.py`）
  - 入参：`{ tool_id, payload }`（`ToolsRequest`）
  - 出参：按工具模块标准化结果
  - 业务：工具分发（已接入 `script_generator`）

### 4) 用户与健康

- `GET /api/v1/user/info`（需 Bearer token）
  - 入参：Header token
  - 出参：`{ user_id, username, is_vip, expire_at }`
  - 业务：会员信息展示

- `GET /health`
  - 入参：无
  - 出参：`{ status: "ok" }`
  - 业务：健康检查

- `POST /api/v1/ping`（`main.py`）
  - 入参：无
  - 出参：连通性测试结果

## B. 关键数据契约（Pydantic / 方法契约）

### Pydantic Models

- `PaymentCreateResponse`（支付创建返回）
  - `order_id: str`
  - `code_url: str`
  - `amount: str`
  - `status: str`

- `LoginQRCodeResponse`（登录二维码返回）
  - `scene_id: str`
  - `qrcode_url: str`
  - `expires_in: int`

- `ToolRequest`（`app.py` 工具请求）
  - `prompt: str`（最小长度 1）

- `ToolsRequest`（`main.py` 工具请求）
  - `tool_id: str`
  - `payload: dict`

### 关键内部契约/函数

- `verify_token_from_header(...) -> str`
  - 解析 Bearer token + DB 校验 + 过期校验
- `_build_wechat_authorization(...) -> str`
  - 生成微信支付 V3 签名头
- `_verify_wechat_signature(headers, body) -> bool`
  - 校验支付回调签名
- `_decrypt_wechat_resource(resource) -> dict`
  - 解密微信回调密文资源
- `generate_scripts(payload) -> Dict[str, Any]`
  - 工具层统一返回格式（success/tool_id/input/result/message/error）

## C. 核心 Routes 对应控制器（文件映射）

- `app.py` 控制器承担：登录、支付、用户、工具 mock、鉴权、数据库迁移
- `main.py` 控制器承担：工具网关分发、固定 token 验证、探针
- 当前仓库无页面路由（无前端页面文件）；“页面”应由外部前端调用这些 API。

## 5. 待办与潜在优化点（基于代码扫描）

### 扫描结果

- 代码内未发现明显 `TODO/FIXME/HACK`（Python 源码范围）

### 主要优化建议（优先级从高到低）

- **敏感信息治理（高）**  
  `app.py` 中直接硬编码了商户私钥、平台公钥、AppSecret 等，应立即迁移到环境变量/密钥管理服务。

- **入口统一（高）**  
  `main.py` 与 `app.py` 各自定义 `FastAPI app` 且路由重叠（如 `/api/v1/tools`、`/health`），建议明确唯一生产入口，避免部署歧义和行为分叉。

- **依赖声明完整性（高）**  
  实际使用了 `cryptography`，但 `requirements.txt` 未声明；应补齐并锁版本策略。

- **文档与实现一致性（中）**  
  SOP 中提到支付固定金额 `49.00`，代码常量为 `1.00`；需统一，避免联调误判。

- **架构规范一致性（中）**  
  SOP 约定工具模块“异步 + AsyncOpenAI”，当前 `tools/script_generator.py` 是同步 `requests` 调用 DeepSeek；建议按规范统一改造。

- **持久化能力（中）**  
  SQLite 适合 MVP，后续若并发与规模上升，建议迁移 MySQL/PostgreSQL，并引入 ORM/迁移工具（如 Alembic）。
